# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

VE-Plan is a virtual event planning platform with independent apps that are not in the same npm/git workspace — each is its own git repository with its own `package.json`/`pubspec.yaml`, dependencies, and lifecycle:

- `backend/` — Node.js + Express + TypeScript + Mongoose (MongoDB) REST API with Socket.IO for real-time notifications.
- `frontend/` — Angular 22 SPA (standalone components, zoneless change detection) with Angular Material (a first-party Material 3 token theme, no Bootstrap) and FullCalendar.
- `mobile/` — Flutter app (Android is the actively developed target; a Flutter-generated `mobile/ios/` platform folder now exists but iOS is not yet built or tested), Riverpod + `jitsi_meet_flutter_sdk`, that consumes the same backend API and mirrors the frontend's feature set. This file and `PROJECT_SPEC.md` focus on `backend/` and `frontend/`; the `mobile-elegance` agent covers the Flutter app.

`backend/`, `frontend/`, and `mobile/` are git-ignored by the outer repo, which tracks only `CLAUDE.md`, `PROJECT_SPEC.md`, and `.claude/`.

Two user roles drive almost all functionality: **organizer** (creates events/sessions, manages registrations, invites attendees, hosts meetings) and **attendee** (discovers/registers for events, accepts invitations, joins meetings). Meetings use 8x8.vc (Jitsi-based) video integration.

## Commands

### Backend (`backend/`)

```bash
npm run dev     # tsc --watch + nodemon dist/index.js, concurrently (typical dev loop)
npm start       # one-shot tsc build then nodemon dist/index.js
npm run build   # tsc build + copy email templates into dist/
npm run pm2:start / pm2:restart / pm2:reload / pm2:stop / pm2:logs   # production process management via ecosystem.config.js (pm2:reload = zero-downtime, graceful drain)
npm run migrate / migrate:status   # build, then run (or list) DB migrations in src/migrations/ — records applied ones in the _migrations collection
```

Migrations (`src/migrations/`) are a hand-rolled runner: each `NNN-*.ts` exports a `Migration` ({ id, description, up }), registered in `migrations/index.ts`. `migrate` runs pending ones in order and is idempotent. Migration 001 de-duplicates the join-table collections and builds the unique/lookup indexes, and must run before the new unique indexes can take effect; schemas set `autoIndex: process.env.NODE_ENV !== "production"`, so in production indexes are only created by the migration. Migration 003 backfills the `timezone` / `starts_at` / `ends_at` fields onto every pre-existing event (default: the server's IANA zone), so `npm run migrate` must run on deploy of the timezone model. Migration 005 backfills `tokenVersion: 0` onto every pre-existing user; the slim-JWT/`tokenVersion` cutover rejects every token issued before it, so `npm run migrate` must run on deploy and all existing sessions (web + mobile) are invalidated (users log in again). Migration 007 creates the 90-day TTL index on `Notification.createdAt` (index-only, no data change), so `npm run migrate` must run on deploy for notification history to start expiring in production. Migration 008 creates the `AuditLog` lookup indexes and its 400-day retention TTL (index-only), so `npm run migrate` must run on deploy of the Phase 7 audit log.

`npm run lint` (ESLint flat config in `eslint.config.mjs` — `@eslint/js` + `typescript-eslint` recommended, non-type-checked) / `npm run lint:fix` lint `src/`; the config relaxes rules to fit the codebase's existing style (`no-explicit-any` off, `no-require-imports` off for the model idiom, unused-vars and a few style rules as warnings) and is expected to exit 0 with a small number of warnings. There is still no backend test suite (out of scope). There is no dedicated `dev` env — running requires `backend/.env` populated (see Environment below).

### Frontend (`frontend/`)

```bash
ng serve                              # dev server, default (development) config, uses environment.ts (localhost)
npm run start:staging                 # serve against the staging backend (environment.staging.ts)
npm run start:prod                    # serve with production configuration
npm run build:staging / npm run build:prod  # builds (rm -rf dist first)
ng test                               # Karma/Jasmine unit tests, all specs
ng test --include='**/auth.service.spec.ts'   # run a single spec file
npm run lint / npm run lint:fix       # ESLint flat config (eslint.config.mjs — @angular-eslint + typescript-eslint), lints src/
```

Nearly every service, guard, and interceptor has a matching `*.spec.ts` — check for one before assuming a unit needs a new test file from scratch. `npm run lint` mirrors the backend's relaxed style (`no-explicit-any` off, unused-vars → warn) plus `@angular-eslint/recommended` and `@angular-eslint/template/recommended`, and is expected to exit 0.

## Architecture

### Backend: layered, route → controller → service → model

Each domain (Event, Session, User, EventRegister, EventInvite, Meeting, Participant, Notification, Email, Auth) follows the same four-file pattern in `backend/src/{routes,controllers,services,models}`:

- **Routes** (`routes/*.ts`) wire `express-validator` `body()` validation chains and middleware directly inline — there is no separate `validators/` directory. Order matters: multer upload → `uploadErrorHandler` (turns Multer's `LIMIT_FILE_SIZE` and `UploadTypeError` into the JSON `413`/`415`/`400` envelope instead of letting them reach the catch-all `500`; also mounted app-wide before the 404 handler as a safety net) → validation array → `jwtAuth` → role middleware (`organizerAuth`/`attendeeAuth`) → controller handler.
- **Controllers** call `isRequestInvalid(req, res)` (in `helpers/utils.ts`) first to short-circuit on validation errors, then delegate all business/DB logic to the matching service. Every handler wraps its body in try/catch and returns a consistent JSON envelope: `{ status: "success"|"error", message, data? }`.
- **Services** contain the actual Mongoose queries/business logic and are imported as `import * as XService from "../services/XService"`.
- **Models** (`models/*.ts`) are exported via `module.exports = mongoose.model(...)` (CommonJS-style, not `export default`), even though the rest of the codebase uses ES `import`/`export`. Cascading deletes are implemented with Mongoose `pre` hooks (e.g. deleting an `Event` cascades to its Sessions, EventRegisters, EventInvites, Meetings, and Participants — see `models/Event.ts`).

Auth: every auth JWT is minted in one place — `helpers/authToken.ts` `signAuthToken(user)` — with a slim, PII-free payload (`{ _id, role, tokenVersion }`) and a 7-day lifetime. `passport-jwt` validates the bearer token's signature/expiry and attaches the raw decoded payload as `req.user`; then `checkUser` (in `middlewares/jwtAuth.ts`, now async) does a per-request `UserService.findAuthContext(id)` lookup: `401 Unauthenticated access.` if the account is gone, `401 Your session has expired. Please sign in again.` if `req.user.tokenVersion !== user.tokenVersion` (legacy pre-cutover tokens have no `tokenVersion` and are rejected), then rewrites `req.user = { _id: <string>, role, name, email, tokenVersion }` from the fresh doc (so `MeetingController` gets current name/email). `tokenVersion` is bumped on password change (`PUT /user/password`, which also returns a fresh token and drops sockets), password reset, so those revoke every prior session on REST and socket. `middlewares/jwtAuth.ts` is an array `[passport.authenticate(...), checkUser]` used as a single middleware. `organizerAuth`/`attendeeAuth` check `req.user.role`; `eventOwnerAuth` additionally loads the event by `req.params.id` (`404` if it no longer exists) and rejects (`403`) any organizer who isn't the event's owner — used on `PUT`/`DELETE /events/:id`, after `organizerAuth` in the chain, and attaches the loaded event as `req.event`. Google/Facebook OAuth (`passport-google-oauth20`, `passport-facebook`) issue the same kind of JWT on successful callback; the OAuth `state` is base64url-JSON `{ nonce, client }` where `nonce` must match a short-lived signed `HttpOnly` cookie (`cookie-parser`, secret `COOKIE_SECRET` || `JWT_SECRET`) — a mismatch is `400 Invalid OAuth state.` — and `client` (`web`/`mobile`, from the `client=mobile` query flag) picks the `veplanauth://oauth?token=` deep link vs. `<frontend>/social_login_redirect`. The callbacks set `Referrer-Policy: no-referrer` before redirecting. `POST /auth/facebook/token` is a redirect-free path for native mobile: `services/FacebookService.ts` verifies a Facebook access token against the Graph API and `UserService.upsertFacebookUser` links or creates the account.

Runs on Express 5 (built-in `express.json()`/`express.urlencoded()`, no `body-parser`) and Multer 2. Request logging is `pino-http` (replaces `morgan`), mounted right after `cors` so `req.log` (a request-scoped `pino` child) exists for every downstream handler: one structured line per request, log level derived from the status code (4xx → `warn`, 5xx → `error`). Each request gets a correlation id — an inbound `x-request-id` is honoured (trimmed, capped ~128 chars) else a `crypto.randomUUID()` is minted — set on `req.id`/`req.log` and echoed on the response `x-request-id` header. `helpers/logger.ts` exports the app-wide singleton `pino` logger for non-request contexts (boot, sweeps, socket, model hooks); `LOG_LEVEL` env overrides the default (`info` in production, `debug` otherwise), and `pino-pretty` is used as the transport outside production. Controllers log caught errors via `req.log.error({ err }, "<Controller>.<handler> failed")`. A catch-all error-handling middleware (registered after the 404 handler in `index.ts`) logs the error (`event: "unhandled_error"`, with `stack`) against the request id and turns any thrown/rejected error into `500 { status: "error", message: "Something went wrong.", data: { requestId } }` instead of leaking it.

Real-time notifications: `libs/socket.ts` authenticates Socket.IO connections via JWT in the handshake — the handshake middleware also re-loads the account (`findAuthContext`) and rejects the connection if the account is gone or `tokenVersion` no longer matches, on every connection including reconnects — joins each user to a private room (`user_<id>`), caps a user at 5 concurrent sockets (oldest dropped on the 6th), logs connect/disconnect, restricts CORS to `corsOrigin()`, and exposes `sendToUser(userId, event, data)` (and `disconnectUser(userId)`) for services (e.g. `NotificationService`).

All routes are mounted under a versioned prefix in `index.ts`: `/api/v1/<resource>` (e.g. `/api/v1/events`, `/api/v1/auth`). Uploaded files (event covers, profile photos) are stored under `dist/photos/` via `multer` and served statically at `/api/v1/static` with `X-Content-Type-Options: nosniff` and `Cross-Origin-Resource-Policy: cross-origin` (so the SPA and mobile app can load them from another origin). The 5 MB cap (`MAX_UPLOAD_BYTES` in `helpers/uploads.ts`) is enforced by multer; a reverse proxy in front of Node must allow at least that much body (`client_max_body_size 6m;`) or it returns its own HTML `413` first.

Observability & ops (Phase 7): a graceful-shutdown path (`SIGTERM`/`SIGINT` → stop HTTP → close Socket.IO → close Mongo → `exit(0)`, 10 s hard cap; `pm2 reload` / `npm run pm2:reload` is the zero-downtime deploy path), plus `process.on("unhandledRejection")` (log-only) and `uncaughtException` (log `fatal`, then drain and `exit(1)`). An **audit log** — `models/AuditLog.ts` + `services/AuditService.record(req, action, target, metadata?)` (best-effort, never throws) — records nine security-sensitive actions (`role.set`, `register.approve`, `invite.send`, `meeting.create`, `meeting.end`, `event.delete`, `account.delete`, `password.change`, `password.reset`) with a denormalised actor, the `x-request-id`, and a 400-day TTL; migration `008-audit-log-indexes` builds its indexes, so `npm run migrate` must run on deploy of this phase. A Prometheus **metrics** endpoint `GET /api/v1/metrics` (`prom-client`, `helpers/metrics.ts` + `middlewares/metrics.ts`) is guarded by a constant-time `METRICS_TOKEN` bearer check (now a production-required env var; `503` if unset, `401` otherwise) and exposes default process metrics plus `http_request_duration_seconds` / `http_requests_total` (low-cardinality route labels) and the `socket_connections` / `email_queue_depth` / `mongo_up` gauges (refreshed on a 30 s interval alongside the sweeps). **Error tracking is log-based** (no Sentry): `POST /api/v1/client_errors` (`routes/clientLog.ts` + `middlewares/softAuth.ts`, rate-limited, soft-auth) logs unhandled SPA errors as one `event: "client_error"` line; the frontend's `core/global-error-handler.ts` (`ErrorHandler`) posts them via `fetch` with dedupe/throttle. `scripts/mongo-backup.sh` / `mongo-restore.sh` and `docs/RUNBOOK.md` cover self-hosted `mongodump` backup, restore, deploy, incident response, and key rotation.

### Frontend: standalone components + role-based lazy-loaded feature routes

The app is fully standalone: `bootstrapApplication(AppComponent, appConfig)` in `main.ts` replaces `AppModule`/`BootstrapModule` entirely — there is no `app.module.ts` or `shared.module.ts`. Every component declares its own `imports: [...]` array of the Material/CDK/CommonModule pieces it needs. `app.config.ts`'s `appConfig` provides the router, `provideZonelessChangeDetection()` (the app runs without `zone.js` in the browser; `zone.js` remains only as a Karma test polyfill), animations, the HTTP client with interceptors, and the native date adapter.

Routing (`app.routes.ts`) splits into:
- Public routes (login, signup, role selection, password reset, email verification, etc.), and
- Two lazy-loaded, role-specific route trees gated by `canMatch: [completeAuthGuard]`: `mod-organizer/` at `organizer/dashboard/**` and `mod-attendee/` at `attendee/dashboard/**`, each exporting a `Routes` array from a `*.routes.ts` file (the old `*-routing.module.ts` + `*.module.ts` pair is gone — there's no module wrapping the routes).

Post-Phase-6 IA: both roles' bottom nav is **Home / Events / My Events / Calendar** — `home` is a role-specific dashboard (organizer overview on `/events/organizer_summary`; attendee personalised feed on `/events/attendee_summary`), not the calendar, which now has its own shared `pages/calendar` route. Event detail is a **persistent shell + routed child tabs** (`…/events/:id/view/{overview,agenda,people}` for organizers, `{overview,agenda}` + a pinned participation panel for attendees; a route-scoped `shared/event-view/event-view-store.ts` carries the event to the tabs). The attendee's old `invitations` / `joined_events` routes `redirectTo` a single merged `mod-attendee/my-events` (`GET /events/my`, segmented All/Invited/Registered/Approved/Attending).

Guards (`guards/`):
- `authGuard` — redirects to `/login` if no JWT in `localStorage` (key `"token"`).
- `hasRoleGuard` — used on the `/role` page; redirects already-role-assigned users straight to their dashboard.
- `completeAuthGuard` — a `CanMatchFn` gating the lazy feature routes: redirects to `/login` if not signed in, to `/role` if the account has no role yet, and to the caller's own `<role>/dashboard/home` if the matched path's role (`organizer`/`attendee`) doesn't match the JWT's role — so a signed-in attendee can no longer reach `organizer/dashboard/**` by URL, and vice versa.

Interceptors (`interceptors/`) are registered via `provideHttpClient(withXhr(), withInterceptors([...]))` in `app.config.ts` (there is no `app.module.ts`), in order: `authInterceptor` (attaches the `Authorization: Bearer` header from `localStorage`'s `"token"` to every `environment.apiUrl` request), `errorInterceptor` (catches every HTTP error and rethrows a typed `models/ApiError.ts` built from the backend's `{ status, message, data? }` envelope — components check `err instanceof ApiError` / read `err.message` rather than `HttpErrorResponse`/`err.error.message`). On a `401` it clears the stored token, then navigates to `login` — but only if a token existed to begin with. It does **not** navigate on `403`/`404` at all (a background request failing shouldn't throw the user off their current page); the old `PRIMARY_RESOURCE` `HttpContext` token and `interceptors/http-context.ts` that used to opt a handful of organizer screens into redirect-on-error are gone, replaced by the route resolvers below.

`provideRouter(routes, ...)` also passes `withComponentInputBinding()` (route params/data bind straight to matching `input()`s), `withRouterConfig({ paramsInheritanceStrategy: 'always' })` (so the event-detail child tab routes — `…/view/overview|agenda|people` — inherit the parent route's resolved `event` and `:id`), and `withNavigationErrorHandler(...)` (a resolver error that isn't a handled 404 surfaces as an error toast via `CommonService` instead of a blank navigation failure). `resolvers/` (alongside `guards/`/`interceptors/`) holds route resolvers — `event.resolver.ts` loads the event for the 6 event-scoped organizer/attendee routes (event-view, registered-users, invite, event-attendees, meeting, meeting/attendees) before the route activates, redirecting to the dashboard's not-found page on a `404` and rethrowing anything else for `withNavigationErrorHandler` to surface. Routes that expose owner-only management (registered-users, invite, meeting, meeting/attendees) set `data.requireOwner: true`; the resolver then also redirects a non-owner organizer to the not-found page (the backend still enforces ownership on every mutating endpoint — this keeps the screen itself unreachable, and the People/Meeting tab links in `event-view` are hidden for non-owners via `EventViewStore.canManage`).

Feature-flagged config lives in `src/environments/environment*.ts` — `apiUrl`, `socketUrl`/`socketPath`, static asset URLs (`profileUrl`/`coverUrl`), the 8x8.vc `appId`/`meeting_domain`, and the OAuth entry-point URLs (`google_oauth_url`/`facebook_oauth_url`). `environment.production.ts` is swapped in automatically by the `production` build configuration (see `angular.json` `fileReplacements`); `environment.staging.ts` by the `staging` configuration.

Services under `services/` are thin HTTP wrappers (one per backend resource, mirroring the backend route names) that return typed `Observable`s using shared response types from `models/Utils.ts`. `caches/` holds services that memoize cross-cutting state used by guards (e.g. `DashboardCacheService.has_role`). `LayoutService` exposes the shell's compact/expanded breakpoint state (consumed by the nav shell and `<app-data-table>`'s card-row fallback); `ConfirmService` (+ `<app-confirm-dialog>` in `components/confirm-dialog/`) replaces every native `confirm()`/`alert()` call with a themed, accessible dialog, including a destructive "type the name to confirm" mode; `CommonService` wraps `MatSnackBar` with four toast severities (`success`/`info`/`warning`/`error`), each with its own colour, icon, and dismiss timing (an error toast never auto-dismisses), and an `error()` overload that accepts a typed `ApiError` directly. All ~60 components are `ChangeDetectionStrategy.OnPush`.

A shared component library lives under `src/app/shared/ui/` — `status-chip`, `avatar`, `empty-state`, `error-state`, `skeleton`, `page-header`, `breadcrumbs`, `form-error`, `submit-button`, `event-card`, `data-table` — each a standalone, signal-`input()`/`output()` component with its own `.spec.ts`, replacing the bespoke status badges/empty-copy/loading spinners/table wiring every screen used to hand-roll. `<app-page-header>` and `<app-breadcrumbs>` read `BreadcrumbService`, which derives a route's breadcrumb trail from its `data.breadcrumb` entry. The app shell itself (`layouts/private/`) is a `100dvh` CSS grid with exactly one scroll container per route (`#main-content`, not `calc(100% - 56px)` against the old fixed toolbar height) — a bottom nav below the tablet breakpoint, a collapsed icon rail at tablet width, and an expanded labelled drawer at desktop width, all reading the same `nav-destinations.ts` list.

Styling/theming (`src/styles/`, `@use`d from `src/styles.scss`, which is the app's only global stylesheet): `_theme-colors.scss` (generated by the `@angular/material:theme-color` schematic from the brand hex, not hand-edited), `_tokens.scss` (the app-level token contract on top of Angular Material's `--mat-sys-*` custom properties — spacing/radius/elevation/motion scales, a `$breakpoints` Sass map, and the `prefers-reduced-motion` global rule; the legacy `--primary-clr`/`--secondary-clr` aliases and the `.text-primary-clr`/`.bg-secondary-clr` utility classes were fully removed in Phase 6 Step 15), `_status-tokens.scss` (four semantic success/warning/info/neutral container/on-container pairs `<app-status-chip>` and the toast severities draw from, generated so they survive a future dark-mode flip without component edits), `_toast.scss` (the `mat-snack-bar` `panelClass` overrides per severity), `_layout.scss` (first-party semantic layout classes — `.stack`, `.cluster`, `.card-grid`, `.form-grid`, `.split`, `.hide-md-down`/`.show-md-down`, `.scroll-y` — that replaced Bootstrap's grid/flex utilities), `_utilities.scss` (spacing/text/sizing utility classes kept under Bootstrap's old names and values, now first-party), `_fonts.scss` (self-hosted `@font-face` for Ubuntu and classic Material Icons, serving from `public/assets/fonts/`; Google Fonts is not used), and `_vendor-fullcalendar.scss` (the `.fc-*` override block). The Material theme itself is defined in `styles.scss` via `mat.theme()` with `theme-type: color-scheme` (emitting the `--mat-sys-*` custom properties as `light-dark(…)`); there is no `rose-red` prebuilt theme and no Bootstrap import or dependency. **Dark mode is live** (Phase 6): `styles.scss` sets `color-scheme: light dark` (follows the OS) and `html[data-theme='light'|'dark']` pins it; `services/theme.service.ts` (Light / Dark / System, `localStorage` key `"theme"`) drives a `data-theme` attribute on `<html>`, mirrored by a pre-paint inline script in `index.html` to avoid a flash, and toggled from the profile-menu **Appearance** submenu.

### Environment configuration

Backend expects a `.env` in `backend/` with (non-exhaustive): `DB_URL`, `JWT_SECRET`, optional `COOKIE_SECRET` (signs the OAuth-state cookie; falls back to `JWT_SECRET`), `FRONTEND_URL`, `CORS_ORIGIN`, `PORT`, Google/Facebook OAuth credentials (`GOOGLE_CLIENT_ID`/`SECRET`/`CALLBACK_URL`, `FACEBOOK_APP_ID`/`SECRET`/`CALLBACK_URL`, optional `FACEBOOK_GRAPH_VERSION`), Gmail SMTP OAuth2 email credentials (`SENDER`, `SMTP_USER`, `OAUTH_CLIENT_ID`, `OAUTH_CLIENT_SECRET`, `OAUTH_REFRESH_TOKEN`, `OAUTH_ACCESS_TOKEN`), optional `UNSUBSCRIBE_EMAIL` (address for the `List-Unsubscribe` header on notification mails; falls back to `SENDER`), optional `LOG_LEVEL`, `METRICS_TOKEN` (bearer token guarding `GET /api/v1/metrics`; required in production), and 8x8.vc Jitsi credentials (`JITSI_APP_ID`, `JITSI_API_KEY`, `PRIVATE_KEY_PATH` — path to the RS256 private-key `.pem`). `EmailService` resolves templates by action name from `src/email_templates/<action>.html` and talks to `smtp.gmail.com` directly; the `SENDGRID_API_KEY`, `RESEND_API_KEY`, `SMTP_SERVICE`, and `*_TEMPLATE` keys still in older `.env` files are not read by the current code.
